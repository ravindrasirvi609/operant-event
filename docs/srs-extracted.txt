1. Executive Summary
Operant Event is a multi-tenant SaaS platform for conference organizers, professional associations, academic institutions, medical societies, event agencies and similar organizations. The platform will manage the end-to-end lifecycle of an event, from conference setup and abstract submission through peer review, acceptance, registration, payment, scheduling, on-site attendance, certificates and post-event reporting.
The system is designed as a configurable platform rather than a single-purpose conference website. Each organization can operate multiple conferences, and each conference can independently configure submission forms, tracks, review rules, registration categories, pricing, sessions, speakers, notification templates and certificate policies. The architecture must enforce strict tenant isolation so one organization or conference cannot access another customer's data.
The baseline implementation uses a modular-monolith backend with NestJS, a Next.js web frontend, PostgreSQL with Prisma as the primary data store, Redis for caching and queues, BullMQ for background work, object storage for files, and provider adapters for payments and communications.
Centralize conference administration into one SaaS workspace.
Replace spreadsheets and disconnected tools for abstract and reviewer management.
Provide configurable workflows without requiring engineering changes for every event.
Protect author, reviewer, payment and organizational data through tenant-aware authorization.
Provide a clean operational workflow for on-site event teams.
Create a technical foundation that can scale from small workshops to large multi-track conferences.
2. Product Vision and Goals
2.1 Vision
Build a reusable conference operating system where an organizer can configure, launch, operate and close a conference from one product while participants, authors, reviewers, speakers and staff each receive focused experiences.
2.2 Business Goals
1. Enable organizations to create and operate multiple conferences under one account.
2. Reduce administrative effort for abstract, review, registration and check-in workflows.
3. Create a SaaS product capable of plan-based pricing and usage-based billing.
4. Allow configuration of event-specific workflows without code changes.
5. Create reusable platform capabilities for future event types such as workshops, seminars, congresses and exhibitions.

5. Product Principles
Configuration over customization: event teams should configure forms and rules without code.
Tenant isolation by default: every data access path must establish organizational context.
Immutable history for critical workflows: submissions, reviews, decisions, payments and audit entries must retain meaningful history.
API-first business logic: important actions must be represented by service-layer operations and auditable APIs.
Asynchronous by design for heavy work: emails, PDFs, exports and large imports must use background jobs.
Provider abstraction: payment, email, file storage and identity integrations should not be hard-wired into domain logic.
Operational simplicity: the event-day workflows must work even under time pressure.

7. Tenant and Organization Model
The SaaS tenancy boundary is the organization. An organization can own multiple conferences. A conference may contain many users, abstracts, registrations, payments, sessions and other event-specific records.

7.1 Tenant Isolation Requirements
Every tenant-owned table must contain organization_id directly or be reachable through a tenant-owned parent.
Every request must resolve current organization context from a verified membership/session, not from an arbitrary client-supplied tenant ID.
Conference-scoped APIs must verify that the conference belongs to the current organization before querying child records.
Background jobs must carry organization_id and conference_id where relevant.
Exports must only include records authorized for the requesting organization.
Administrative support access must be explicit, auditable and time-bounded where practical.

10. Abstract Management
Abstract management is a core domain. The system must support configurable forms, multiple authors, version history, file attachments, submission numbering, status transitions, screening and later review/decision workflows.
10.1 Abstract Lifecycle
DRAFT -> SUBMITTED -> SCREENING -> UNDER_REVIEW ->
REVISION_REQUIRED -> RESUBMITTED -> ACCEPTED / REJECTED / WAITLISTED
                                   |
                                   +-> SCHEDULED -> PRESENTED
10.2 Submission Form Requirements
Conference administrators can define form sections and fields.
Field types include text, long text, rich text, number, date, select, multi-select, radio, checkbox, file and URL.
Fields can be required/optional and can have validation rules.
Field order is configurable.
Fields can be enabled or disabled without deleting historical submitted values.
Submitted form data is versioned with the abstract version.
Large content and files must be stored using appropriate limits and object storage.
10.3 Submission Numbering
The system should generate a human-friendly submission number per conference, such as A-000123. The internal primary key remains a non-sequential UUID/CUID-style identifier. Submission number uniqueness is guaranteed within the conference.

25. Search and Data Access
The initial release should use PostgreSQL indexes and full-text/case-insensitive search where practical. External search engines such as OpenSearch can be introduced later for high-volume cross-field search.
Search must always be tenant-scoped.
Search results must respect role permissions and blind-review visibility.
Exact identifiers such as submission number and registration number should be indexed.
Pagination should use stable ordering and limit result size.
Large datasets must avoid unbounded API responses.

28. Security Requirements
All production traffic must use TLS.
Passwords must be hashed using a modern password hashing algorithm; plaintext passwords must never be stored.
Session and refresh tokens must be stored/handled securely and preferably use HTTP-only, Secure cookies for browser-based sessions.
All input must be validated and normalized at API boundaries.
Authorization must be server-side; UI hiding is not a security control.
Rate limiting must protect login, password reset, public forms, webhooks and high-cost endpoints.
Webhook endpoints must validate signatures and implement idempotency.
Sensitive secrets must be managed through environment/secret managers, not source control.
File upload endpoints must enforce MIME/type, size and ownership constraints.
Exports, support access and impersonation must be auditable.
Production database backups must be enabled and restore procedures tested.

29. Privacy and Compliance Requirements
The platform will process personal data including names, email addresses, phone numbers, affiliations, payment-related references and attendance. Exact legal obligations depend on customer geography and event type; the product must therefore provide configurable retention and privacy controls rather than assuming one jurisdiction.
Collect only fields needed for stated event purposes.
Document a privacy policy and consent language for public registrations where required.
Provide controlled data export for customer administrators.
Provide deletion/anonymization tools subject to legal, financial and audit retention requirements.
Avoid exposing participant contact details publicly unless explicitly configured.
Retain financial records according to applicable legal/accounting policy.
Separate operational audit logs from user-visible profile data.

Appendix C - Example End-to-End Journey
A conference manager creates “Operant Medical Summit 2027”, defines two tracks and publishes a configurable abstract form. An author creates an account, adds co-authors, saves a draft, then submits before the deadline. The system assigns the abstract to three reviewers based on track and expertise while excluding declared conflicts. Reviewers complete scores; the track chair marks the abstract “Revision Required”. The author submits version two. The chair then marks it “Accepted - Oral”. The author receives an acceptance notice and registers using an author category. Payment is confirmed through a provider webhook, a registration number and QR are generated, and an invoice is issued. The conference manager assigns the accepted abstract to Session 4. On event day, registration staff scan the attendee QR, record check-in and optionally print a badge. After participation, the certificate job verifies eligibility and generates a PDF with a unique verification code. The attendee can validate the certificate publicly without exposing unnecessary personal information.
